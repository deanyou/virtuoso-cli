| 项 | 值 |
|----|-----|
| RAMIC Bridge 会话 | `<SESSION_ID>`，port `<SESSION_PORT>` |
| Virtuoso | IC26.1 |

| 工作副本 | 基线 `target/debug/vcli`（main 等价）与各 PR 分支各自独立编译的二进制 |

### 1.2 方法

遵循 `.claude/skills/verify-virtuoso-cli/SKILL.md` 的分级规程：

- **Tier A**（客户端侧）：Rust 工具链 / Python 即可证明。
- **Tier B**（穿过 bridge 进入活着的 Virtuoso）：需要真实会话、真实 OA 数据库、真实 license。
- 每个驱动都同时采集 **stdout、stderr、exit code**，并读取 `$VB_HOME/cache/virtuoso_bridge/history/cmd.jsonl` 作为副作用证据。
- `--dry-run` 只证明请求整形，**不作为 bridge 通过的证据**。
- `fake` executor 是**对 harness 的回放**，不是 Virtuoso 的 mock，`fake` 通过永远不等于 Tier B 通过。

### 1.3 一个必须写明的环境限制

`scripts/doctor.sh` 对本次会话报 `tier_b: unreachable`，但**这是误报**：doctor 探测的是配置里的端口 `<CONFIG_PORT>`，而本会话在 `<SESSION_PORT>`。bridge 存活性是用

```
vcli --format json rpc call --method util.ping --params '{}'
```

单独证明的，返回 `{"status":"ok"}`。同理，`skill.exec` / `vcli skill exec` 会被客户端侧的能力闸门拦下（`CapabilitySet::allows_raw_skill()`），需要 `VCLI_CAPABILITY=admin` 才放行 —— 这是**设计行为**，不是缺陷。

## 2. 逐 PR 结论

### 2.1 PR #127 — X11 cookie / DISPLAY 修复

**变更内容**（1 个 commit，2 文件，+625 −19）：把 helper 命令里的 cookie 从「尾部追加 ` XAUTHORITY=<path>` token」改成「`env DISPLAY=… XAUTHORITY=… ` 前缀」，同时在 `resolve_envs` 的显式 display 分支上补上 cookie 来源。

**关键发现：这个 PR 的分支基线早于 main 对同一个缺陷的修复。**

- PR #127 的 merge-base 是 `5826254`（2026-10-08）。
- main 里的 `6f67269`（2026-10-30，"fix(x11): stop the helper from reading XAUTHORITY as the DISPLAY"）**已经在 origin/main 上**（`git merge-base --is-ancestor 6f67269 origin/main` → YES）。
- `6f67269` 在 `resources/x11_dismiss_dialog.py` 的 argv 解析里加了 `elif "=" in a:` 分支，把 `KEY=VALUE` token 当作环境覆盖消费掉，而不是当成位置参数 DISPLAY。

也就是说，PR 描述里的第二个缺陷（helper 把尾部的 `XAUTHORITY=` token 误吃成 DISPLAY）**在 main 上已经不存在了**。PR 分支上的 helper 里没有这个分支，所以 PR 在自己的基线上是必需的，但那个基线已经过时。

**反事实验证**（对 pre-`6f67269` 的 helper 做对照）：

| helper 版本 | argv 形式 | 结果 |
|---|---|---|
| pre-`6f67269` | main 式尾部 ` XAUTHORITY=…` token | `cannot open display 'XAUTHORITY=…'` |
| pre-`6f67269` | PR #127 式 `env` 前缀 | OK |
| main（含 `6f67269`） | main 式尾部 token | **OK**（token 被 `KEY=VALUE` 分支消费） |

**实机差分结果**（两个二进制，同一 live 会话）：

- `window list-windows-x11`：两边都是 **99 个窗口**，窗口集合完全一致。
- `window action-x11 --operation screenshot`：两边产出 **byte-identical** 的 PNG（95452 B，md5 `d738c1fb61117f23e4f8c49478bd5992`，内容是 `<WORK_LIB> <CELL> layout` 窗口，可见 `<BLOCK_A>` / `<BLOCK_B>` 版图块）。
- 唯一可观测差异：显式 `--display` 路径下 `xauthority` 字段从 `null` 变成真实 cookie 路径（已脱敏为 `<XAUTHORITY>`）。**但**因为本机 `xhost` 给了 `SI:localuser:<USER>`，cookie 是否被强制对连接结果没有影响，差异只能从 JSON 字段看出来。

**回归测试**：`cargo test --lib x11` → 133 passed / 0 failed；helper 单测 30 OK。

**结论与建议**：

1. PR 描述的两个缺陷里，**缺陷 (B)（helper 误解析）已被 main 的 `6f67269` 修掉**，PR 当前的 Rust 改动（`env` 前缀）在 main 上不再修任何东西。
2. **缺陷 (A) 仍然存在**：`origin/main` 的 `resolve_envs`（`src/transport/x11.rs:3134`）在 `Some(d)` 分支仍然是 `xauthority: None` —— 显式指定 `--display` 时 cookie 完全不被解析，helper 会带着 `XAUTHORITY` 的**空值**去连远端 display。这是一个真实的、尚未修复的缺陷。
3. 因此：**不建议按现状合并**。建议把它改基到当前 main，**只保留缺陷 (A)** 的修复（显式 display 分支从 `detect_envs()` 里捞 cookie），并补一条针对 `resolve_envs` 的测试。`env` 前缀改造可以一并保留作为清理，但它不再是「修 bug」，别再那么描述。
4. 注意 `#127` 是 draft，作者可能本来就在等这个结论。

1. **需要真实 Maestro 环境**。工作流会跑 `maestro.open_session` / `maestro.run` / `spectre.run`，本机没有 maestro view（见 §2.2），这条路径本轮 `verified-unreachable`。

4. **`run.py` 有 shell 注入面**。`run_vcli_command()` 用 `subprocess.run(cmd, shell=True, capture_output=True, text=True, timeout=timeout)`；`cmd` 由 `action_to_vcli()` 拼成字符串，其中参数值来自 YAML 的 `args`，只有「含空格或双引号」时才加双引号（`run.py:99-101`），**不转义** `;` `|` `` ` `` `$()` 等 shell 元字符。YAML 里写 `args: {lib: "a; id"}` 就会执行第二条命令。这条违反仓库 CLAUDE.md 的红线「外部命令用 `Command::new()` + 独立参数，不做 shell 拼接」。建议改用 `shlex.split()` 或直接 `subprocess.run([...])` 列表形式。
5. **文档与代码不一致**。`SKILL.md:137` 写「不支持 `{{variable}}` 替换，参数需直接写在 YAML 中」，但 `run.py:126-129` 恰恰实现了 `{{key}}` 替换（把 context 里的值替换回 args）。两处说法相反，需要作者确认哪个是意图。
6. **两套命令拼装器**。`run.py` 的 `action_to_vcli()` 和 `verify.py` 里的另一套构造逻辑会漂移，建议合并。

### 2.5 PR #135 — russh 0.64.1 → 0.65.0（**已评审：CI 红，不可合并**）

**元数据**：`build(deps): update russh requirement from 0.64.1 to 0.65.0`，head `e92ad67`，1 个 commit，1 个文件，**只改 `Cargo.toml` 一行**（`Cargo.lock` 在 `.gitignore:3`，不受版本控制，lock 由构建时解析）。

**结论：FAIL —— CI 在 head `e92ad67` 上是红的，且原因就在这个 PR 本身。**

**证据 1（本地复现）**：

| 命令 | 结果 |
|------|------|
| `cargo build --features native-ssh` | **通过**（二进制本身没问题） |
| `cargo test --features native-ssh` | **编译失败**：`error[E0053]: method 'auth_publickey' has an incompatible type for trait` |

报错点 `src/transport/native.rs:1770`：

```
expected `russh::server::VerifiedPublicKey<'_>`, found `&russh::keys::PublicKey`
```

russh 0.65 把**服务端** `Handler::auth_publickey` / `auth_publickey_offered` 的参数从 `&PublicKey` 换成了 `server::VerifiedPublicKey<'_>`（定义在 `russh-0.65.1/src/server/mod.rs:235`）。仓库虽然在 `src/transport/native.rs` 里实现的是**客户端** `russh::client::Handler`，但同一文件底部 `#[cfg(test)] mod tests`（约 1200 行起）内嵌了一个**进程内的 russh 服务端测试夹具**，它实现的是服务端 `Handler`，因此被 breaking change 击中。

**关键点：只跑 `cargo build` 看不出问题**，必须 `cargo test --features native-ssh --all-targets` 才会炸。

**证据 2（CI 权威结论）**：`e92ad67` 上的 check-runs 有 4 个 job 失败 —— `ubuntu-latest / native-ssh`、`macos-latest / native-ssh`、`windows-latest / native-ssh`、`Windows native-ssh build`，全部 failure。触发它们的是 `.github/workflows/ci.yml:68-70` 的 `cargo check/test/clippy --features native-ssh --all-targets`，以及 `.github/workflows/integration.yml` 的 `features: [default, native-ssh]` 矩阵。

**修复（一行，已在临时副本验证）**：

```rust
// src/transport/native.rs:1770
async fn auth_publickey(
    &mut self,
    _user: &str,
    _key: russh::server::VerifiedPublicKey<'_>,   // 原来是 &russh::keys::PublicKey
) -> Result<Auth, Self::Error> {
```

改完后整套 `cargo test --features native-ssh` 全绿，测试计数与基线完全一致（1372 / 1535 …），说明**没有测试被静默跳过**。注意 `russh::keys::ssh_key::VerifiedPublicKey` 是**错误路径**（E0425 找不到该类型），正确路径是 `russh::server::VerifiedPublicKey`。

**对「SSH 腿无测试覆盖」这一顾虑的修正**：SSH 传输腿**是有**单元测试的 —— `src/transport/native.rs` 的进程内 russh 服务端夹具共 18 个测试，覆盖连接复用、并发 channel、远端断连健康检查、keepalive、SFTP 往返、host-key 路径。所以 `cargo test --features native-ssh` 变绿**是有效证据**，比 `cargo build` 强得多。残留的缺口只有一个：夹具不是真实 OpenSSH 服务端。不过既然本 PR 只需「重新让既有代码适配新版本」，18 个测试 + CI 三平台矩阵已足够背书，**不必**为这个 PR 单独安排实机 SSH 驱动。

**其他**：`ssh-key 0.7.0-rc.11` 是 PR 之前就存在的，不本 PR 引入。`cargo audit` 未跑（本机未安装 cargo-audit），建议 CI 侧补。**依赖版本核对**：PR 标题写 "from 0.64.1"，`origin/main` 的 `Cargo.toml` 现在写的也是 `0.64.1`（此前报告误记为 0.63.1，已更正），版本声明与 main 一致，无需再确认。

**建议**：合并前必须打上那一行修复（或直接 dependabot rebase 到 russh 0.65.1 后再适配），让 4 个红 job 转绿。

### 2.6 PR #136 — 双技能树同步机制（**已评审：机制成立，但守护它的 CI 门当前是死的**）

**元数据**：`feat(skills): 双技能树同步机制（.claude 正本 → .agents Codex 镜像）`，head `456a6af`，8 个 commit，98 文件，+21626 −659。

**结论：机制本身离线可验证且成立；但 PR 带着三个必须先解决的问题，其中一个让 PR 的核心卖点（CI 里的漂移门）在合并后依然跑不起来。**

**机制本身是有效的（本地实测）**：

- `python3 scripts/sync_skills.py --check` → 退出 0，`no drift: .agents/skills mirrors .claude/skills`；
- `--strict-pending` → 退出 0，pending 列表已清空；
- 漂移**双向都能检出**（正本改了就报、镜像单独改了也报）；
- 装上 numpy / Pillow / scipy 后，`run-skill-tests.sh` 全绿：每棵树 8 个套件 / 435 个测试，与 PR 声称一致。

**问题 1（阻塞级）：守护这个机制的 CI 门今天是红的，而且这个红是 main 上就有的存量问题。**

`456a6af` 上的 check-runs：`Skill tests (py3.9)` 与 `Skill tests (py3.13)` 两个 job **全部 failure**：

- py3.9 job：`version '3.9' not found for Ubuntu 26.04`（runner 镜像已不提供 3.9）；
- py3.13 job：退出码 1 —— `virastack-auto-allow` 的测试 import numpy / scipy 失败，而 `.github/workflows/skill-tests.yml` 只装了 `pytest`。

这个红**不是本 PR 引入的**：`main` 上从 `cb45098` 起就已经红。后果是 `run-skill-tests.sh` 在 `.claude` 那一棵树就 `exit 1`，**`.agents` 那一棵树永远轮不到**——也就是说，本 PR 想证明的「双树都被测到」在 CI 里**一次也没有真正发生过**。要让这个 PR 的主张成立，得先修掉 py3.9 与 numpy/scipy 依赖两个存量问题。

**问题 2（内容缺陷）：适配规则 A5 把路径改写到了一个不存在的目录。**

A5 规则是 `.claude/` → `.Codex/`。但本机的 Codex 布局是：仓库内镜像树 = `.agents/skills`，全局 Codex home = `~/.codex/`（小写）。`.Codex/`（大写、且带尾斜杠）这个路径**在任何地方都不存在**，实际是错的。

后果（PR 自带的镜像树里实测）：**6 个文件共 20 处**引用坏掉 —— `sim-plot` 9、`history-evolve` 4、`verify-virtuoso-cli` 4、`ocean-netlist-regen` 1、`skill-review` 1、`virtuoso-gui-debug` 1。其中 `skill-review` 的发现命令直接失效：

```
find .Codex/skills ~/.Codex/skills -name "SKILL.md" 2>/dev/null | head -30
# → 无输出（静默失败，不报错）
```

**已验证的修复**（在临时副本改完后重跑同步）：把 A5 改成 `~/.claude/` → `~/.codex/`，并新增 A7 `.claude/` → `.agents/`。重跑同步后 `wrote 6 file(s)`、`no drift`，`.Codex/` 出现次数从 20 降到 **0**，`.agents/skills` 引用变成 19 处，`~/.codex/` 引用恢复正确：

```
.agents/skills/skill-review/SKILL.md:14: find .agents/skills ~/.codex/skills -name "SKILL.md" 2>/dev/null | head -30
```

**问题 3（次要）：frontmatter 的 `author:` 被顺手改成了 Codex。**

A3/A4 是整文件文本作用域的规则，把 `author: Claude Code` 一并改成了 `author: Codex`，6 个 frontmatter 的作者署名被伪造。建议把 A3/A4 限定在正文字符串上，不扫 frontmatter 的 `author` 字段。

**问题 4（流程）**：`WORKFLOW-PATCH.md` 里的 `skill-tests.yml` 改动（加 `.agents/skills/**` 与 `scripts/sync_skills.py` 的 path filter）**尚未落进 yml**——PR 描述明说这一步需要仓库主人用真 git 推。不落进去，CI 连「这个脚本被改过」都触发不了。

**遗留问题（未在 PR 中解决）**：`sync_skills.py` 的 manifest 只显式声明了少数 skill，其余约 27 个走**默认镜像**行为。默认镜像对 `skill-review` 这类靠路径字面量定位 skill 的 skill 正是雷区（见问题 2）。建议把每个 skill 的 mode 显式声明出来，别靠默认值。

**建议**：先修 CI 存量红（py3.9 + numpy/scipy）→ 再改 A5/A7 → 修 frontmatter `author` 作用域 → 落 `WORKFLOW-PATCH.md` → 显式声明全部 skill 的 mode。在这之前不要合并。
