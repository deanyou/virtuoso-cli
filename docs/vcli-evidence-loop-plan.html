P0 已发现的核对点

路由拒绝与执行真值要区分

experience.py 将 rejected 的路由标为 VERIFIER_CONFIRMED。审计与校准需排除这种策略判断，避免混入动作成功概率。

通道过滤字段需要对齐

experience_retrieval.py 对 case 查询使用 channel；当前 case DDL 未声明此列。需核对生产迁移或按 event_refs 关联事件。

静默失败不能当作记录完整

经验写入存在吞掉异常的路径。补齐诊断与记录完整性标识；不完整 run 进入观察池，排除候选支持与经验校准。

用证据验收，不用功能数量验收

先证明闭环可信、建议相关、执行行为稳定，再讨论自动化程度。

固定验收条件
01 / 证据链

每条候选都能回到原事件

run、step、干预、followup run、Verifier 与 manifest 可关联；丢失证据明确标记，不能晋升为可信支持。

02 / 统计口径

已验证与未知分开计数

按独立 run / 干预 episode 去重；展示“通过 / 已验证”“未知 / 总尝试”。路由拒绝不是动作验证，未知不是失败。

03 / 执行隔离

observer 不改变任务行为

禁用或启用记录时，任务命令、权限、重试与返回结果保持一致；不增加 SSH 调用，不在执行线程调用模型或挖掘脚本。

04 / 候选确定性

同一数据得到同一结论

快照 hash、schema / miner 版本、参数与稳定排序留档。候选门槛属于报告配置，不控制 Runtime。

05 / 建议相关性

保留正例、反例与 NO_MATCH

匹配工具 / scenario / 目标类型等适用条件。旧版本、条件不符和未知记录不被自动推荐；当前环境仍由实时探测确认。

06 / 受控生效

采纳不等于自动执行

人工选择候选后，补代表性回归、独立评估和代码评审。保留原版本与采纳记录；撤销后恢复原建议或规则。

真实收益：重复干预率下降，误建议率不升

先记录基线，再在相同条件的保留案例上对比：需要重复人工修正的 run / 可比 run；不适用建议 / 人工评审建议；实际任务完成与耗时作为辅助指标。没有基线就不填收益百分比。

验证方式

  • 契约、去重、过滤、证据缺失与确定排序：离线 fixture 验证。
  • 记录开关前后：fake executor 对比命令与结果。
  • 按时间 / 任务分离开发集与保留集；不在搜索案例上宣称泛化收益。
  • 最终验收使用自然产生的真实任务；保留样本不足时报告不确定性。

候选报告应保留什么？
candidate_id / schema_version / miner_version / snapshot_hash
适用条件：目标类型、工具版本、scenario 版本、通道、阻塞签名
建议类型：检索别名 / 检查前置条件 / 操作流程 / Verifier 候选
统计口径：独立 run 数、验证通过数、验证失败数、未知数
证据：支持案例、反例、原事件引用、验证产物引用
评审：pending / accepted / rejected，理由、评审人、时间
采纳：对应回归、独立评估、代码版本、撤销路径

门槛由真实分布和评审能力确定；少样本候选可以展示，但不承诺有效，也不自动生效。Verifier 候选的采纳必须保持既定规格与真值来源。
