## ✅ step 6 前置：Tier2 进程身份校验（提交 255cc8b，已推送）

依据设计文档 "Stop and crash recovery"（spec:239-275）：**PID 单独绝不足以标识进程（PID 会复用）**，
Tier 2（daemon 无响应、无法完成 nonce 挑战）必须先做 OS 级身份三属性匹配，否则不得发信号。

- **新增 `src/transport/identity.rs`**（`#![allow(dead_code)]`，待 step 6 daemon 生命周期消费）：
  - `ProcessIdentity { executable_path, pid, start_identity }`；
    `matches()` 要求 **三属性全等**，且 `start_identity != 0`、路径非空（读不到属性即 fail-closed，
    绝不允许「空 == 空」判等）。
  - `IdentityError::{NoSuchProcess, UnsupportedPlatform, Unreadable}`；
    `Refusal::{Unverifiable, Mismatch, ProcessGone}` + Display。
  - `authorize_signal(recorded) -> Result<(), Refusal>`：只有三属性与运行中进程完全一致才 `Ok`；
    **无法建立身份时一律拒绝**，绝不退化成「只信 PID」。
  - 平台实现：`linux` 读 `/proc/<pid>/exe` + `/proc/<pid>/stat` 第 22 字段 starttime
    （comm 含空格/括号 → 按**最后一个 `)`** 切分，索引 19）；`macos` 用 `libc::sysctl`；
    `windows` 与未知平台显式 `Err(UnsupportedPlatform)` → 拒绝发信号
    （顺带堵住设计文档点名的"Windows 上无条件 `taskkill /F`"缺口）。
  - 11 个单测：三属性全等 / PID 复用（同 PID 不同 start）/ 同 PID 同 start 不同路径 /
    start=0 不匹配 / 空路径不匹配 / 不同 PID / 不可验证即拒绝（不静默成功）/
    macOS live：`current()` 可读、`of_pid` 自洽、`authorize_signal` 对自身进程 `Ok`、
    start 时间在合理范围、exe 路径与 `current_exe()` 同名。

### 🔑 macOS sysctl 关键点（踩坑 + 结论，可复用）

1. **`KERN_PROCARGS2`(49) 是顶层 `KERN_*` 项，不是 `KERN_PROC`(14) 的子项**。
   正确 MIB 是 `[CTL_KERN=1, KERN_PROCARGS2=49, pid]`（**3 元素**）；
   写成 `[1, KERN_PROC=14, 49, pid]`（4 元素）会返回 **ENOENT**。
2. `KERN_PROC_PID` 用 `[CTL_KERN=1, KERN_PROC=14, KERN_PROC_PID=1, pid]`（4 元素），返回 `kinfo_proc`（len=648）。
3. **`kp_proc.p_starttime` 位于 `kinfo_proc` 偏移 0**（`extern_proc` 首成员是 `p_un` union，
   其 `__p_starttime` 是 `struct timeval`）→ 直接读前 8 字节 `i64::from_ne_bytes` 即为 epoch 秒，
   **无需复刻整个随架构变化的 `kinfo_proc` 结构体**。
4. `KERN_PROCARGS2` 布局：`i32 argc` + 一串 NUL 结尾字符串，**第一个字符串即可执行文件路径**。
5. 本沙箱**不拦 `sysctl`**（`[CTL_KERN, KERN_OSTYPE]` 正常返回 "Darwin"），
   但**拦 `ps` 子进程**（`Operation not permitted`）→ 与 `ps` 的交叉校验必须写成
   "spawn 失败就跳过"，不能当硬断言。

## ✅ 修 env 竞态（提交 23638bf，已推送）—— 已完成，见下

**根因（最终确认）**：四个模块各自 `static ENV_LOCK`，注释都写 "global"，但**是四个互不相关的
互斥量**：`commands/session.rs`、`client/bridge.rs`、`runtime_paths.rs`、`tests.rs(config_tests)`。
于是 `bridge` 测试在其锁内 `remove_var/set_var("VB_PROFILE")`，而 `session` 的 `check_cross_user()`
在其**自己的**锁内读 `VB_PROFILE` → 两把锁不互斥 → 竞态。

**结构要点（易踩）**：
- `src/tests.rs` 声明在 **`main.rs:24`**（vcli bin），**不在 lib.rs** → 与 lib 测试**进程隔离**，
  跨进程不会互相污染 env。
- 但 `runtime_paths` 被 **lib.rs / main.rs / vtui.rs 三个 crate 根**各 `mod` 一次 →
  共享锁必须在**三个 crate 根都声明** `#[cfg(test)] mod test_env;`，否则某 crate 编译不过。
- `src/tests.rs` 的 `config_tests` 用 `pub(super) use crate::test_env::ENV_LOCK;` 重导出，
  下游 `use crate::tests::config_tests::ENV_LOCK;`（两处）无需改动。

**改动**：
- 新增 `src/test_env.rs`（`#![cfg(test)]`）：单一 `pub static ENV_LOCK` + `pub fn lock()`
  （`unwrap_or_else(|e| e.into_inner())` 吞 poison）。
- 三个 crate 根各加 `#[cfg(test)] mod test_env;`。
- session / bridge / runtime_paths 改用 `crate::test_env::lock`（别名 `env_lock`）；
  移除各模块 `use std::sync::Mutex;`（否则 clippy `-D warnings` 报 unused import）。
- **所有加锁点改为 recover-from-poison**（含 `tests/daemon_user_guard.rs` 的 6 处 `.unwrap()`）。
  此前首个断言失败污染互斥量 → 把 1 个真失败放大成 6 个失败并掩盖真因。

**验证**：改前连续 3 次全量 `cargo test` 有 2 次各失败 5~6 个；
改后 **25 次 lib + 6 次全量连续通过**（期间出现 1 次单测失败，但**已不再级联**，仅 1 个）。

**残留风险（未消除，需后续）**：未加锁的「读方」（大量直接调 `Config::from_env()` 的测试）
仍可能与持锁写方在 `std::env` 层面并发读。彻底解决需 `serial_test`（**需联网新增依赖**）
或 `--test-threads=1`。已排除其它嫌疑：无 `.env` 文件（dotenv 是 no-op）、无 `set_current_dir`、
`Command::env()` 只影响子进程。

## ✅ fix：identity.rs macOS 缺失 PID 判定（提交 7e4fc76，已推送）

写 `daemon_lifecycle` 时反查发现**自己上轮埋的 bug**，两个独立问题：
1. 按格式化文本匹配 `"ESRCH"` → 永不命中。`io::Error` 的 Display 是
   `"No such process (os error 3)"`，**不含 "ESRCH"**。改为按 **errno 码**映射
   （`sysctl_bytes` 改返回 `Result<usize, i32>`，由 `map_errno()` 统一映射）。
2. **更关键**：实测 pid 41000 / 99999 / 999999 → macOS 上 PID 不存在时 `sysctl`
   **返回 ret=0（成功）且 len=0**，根本不报 ESRCH；存活 PID 返回 len=648。
   → 判据必须是 **len == 0**，errno 映射仅作兜底。
   影响：此前死亡 PID 误报 `Unverifiable`，上层无法区分「进程已消失（可清理）」与
   「无法验证（必须拒绝）」。
3. 测试**不能用 `u32::MAX`**：转 `c_int` 为 -1，内核特殊处理（ret=0 len=0 而非报错）。
   用 999_999（macOS pid_max=100000）。
新增 2 个回归测试：`of_pid(999_999) → NoSuchProcess`、
`authorize_signal(死亡 PID) → ProcessGone`。

## ✅ 接线 assess 到 SSHClient::stop（提交 f3c3a65，已推送）

**关键约束**：OpenSSH / v1 状态**不记录**身份三属性 → 若照搬 `assess` 会返回
`Unverifiable`，从而让 `tunnel stop` 拒绝停止 OpenSSH 隧道 = **重大回归**。
故设计成「**有身份记录才走新逻辑**」，OpenSSH 路径行为逐字不变。

- 新增 `StopDecision::{Signal, Skip(reason)}` + `stop_decision(state, pid)`：
  - `recorded_identity(state).is_some()`（native daemon）→ `assess(...)`：
    `Alive | UnresponsiveButIdentified → Signal`；`Stale → Skip("no longer running")`；
    `Unverifiable(reason) → Skip(reason)`。
  - 否则 → `openssh_stop_decision`（`#[cfg(unix)]` 走 `verify_ssh_pid`；
    `#[cfg(not(unix))]` **保持原样盲信 PID**，注释标明这是设计点名的缺口）。
  - Tier 1 的 `challenge` 闭包暂恒 `false`（IPC 客户端随 native daemon 落地），
    所以现在只会走到 Tier 2 —— **方向保守：只会拒绝，不会放行**。
- `stop()`：按 profile 加载一次 `TunnelState::load_with_profile(...).ok().flatten()`，
  再据裁决决定是否发信号；拒绝时 `tracing::warn!` 给出具体原因。
- 5 个新测试（含核心安全性质）：无身份状态不走 native 路径 / 无状态回退 OpenSSH /

## ✅ 修两个既有 bug（提交 70a57fd，已推送）

### bug 1（主要）：macOS 上 `tunnel stop` 从不杀进程
`verify_ssh_pid` 只读 `/proc/<pid>/cmdline`，而 **macOS 没有 /proc**（实测 `test -d /proc`
为 false）→ 对任何 pid 恒 `false` → `stop()` 走 else 只 warn
"PID x is not an SSH process, skipping kill"，**ssh 隧道进程被留下**。
修复：按平台拆成三个 `#[cfg]` 版本 ——
- linux/android：继续用 `/proc/<pid>/cmdline`（行为不变）
- macos：改用 `identity.rs`（sysctl `KERN_PROCARGS2` 取可执行文件路径）+ `is_ssh_executable()`
- 其它：保持原样盲信 PID（注释标明是设计点名的缺口）

### bug 2：`is_tunnel_alive()` 在非 unix 上杀掉被测进程
原实现执行 `taskkill /PID <pid> /F` 再以 `is_err()` 判存活 —— **探测即破坏**，
且返回值与事实相反。改为 `tasklist /FI "PID eq <pid>" /NH` 非破坏性探测
（解析第二列是否等于 pid；spawn 失败则 false）。
该函数**当前无调用方**（全仓仅定义处一处），故无回归风险，但留着是雷。

### 测试（macOS 可跑，均为回归性质）
- `ssh_executable_detection`：纯谓词（`/usr/bin/ssh`→true，`/usr/bin/python3`→false）。
- `macos_verifies_a_real_process_by_its_executable`：**真起进程**验证 —— 把 `/bin/sleep`
  复制成名为 `ssh-standin` 的可执行文件并 spawn，断言 `verify_ssh_pid` 为 **true**；
  对照组 `/bin/sleep` 断言 false。旧实现在此**必然失败**，故是有效回归测试。
- `dead_pid_does_not_verify_as_ssh`：死亡 pid 返回 false 而非 panic/盲信。
- 子进程用 `reap()`（kill + wait）回收，规避 clippy `zombie_processes`。

验收门：fmt ✓ / clippy `-D warnings` ✓ / `cargo test` 0 failed（lib 682）✓ / `git diff --check` ✓。

### 复用教训
- **平台专有判据要按 `#[cfg]` 拆函数，不要在一个函数体里塞 `#[cfg]` 块 + `/proc` 假设**；
  macOS 无 /proc 是硬事实，任何依赖它的校验都会静默恒 false（fail-closed 但功能失效）。
- **测试"进程是否 ssh"不要真起 ssh 连接**：复制 `/bin/sleep` 成带 ssh 名字的可执行文件
  即可在沙箱内验证机制本身，对照组用原名 —— 便宜且确定。

## ✅ 状态清理按裁决门控（提交 84e4cd3，已推送）

设计里「清理需证据」的另一半：**只有 Stale 才允许丢弃状态文件，Unverifiable 必须留下**。

- `StopDecision::Skip(String)` → `Skip { reason, clear_state }`；
  `clear_state` 区分「已证明消亡」与「只是查不出来」。
- **抽出纯函数 `verdict_to_decision(verdict, pid)`** —— 关键决策：原先 `Unverifiable`
  分支**无法通过真实 pid 稳定触发**（macOS 上缺失 pid 经 identity.rs 是可证明的
  `ProcessGone` → `Stale`，不是 Unverifiable）。抽成纯函数后四个 Verdict 的映射
  **在任何平台都确定可测**。（第一版测试就踩了这个坑：以为 999_999 会得 Unverifiable，
  实际得 Stale —— 测试前提错了，是测试的问题不是实现的问题。）
- `stop()`：`clear_state=false` 时**提前返回** —— 不清状态文件、**也不跑 cleanup_remote**，
  并 warn 提示手动处理。理由：既然没证明任何事，就不该销毁任何东西；清掉远端 scratch
  可能弄坏仍在运行的 daemon。
  该分支仅在「状态记录了身份三属性」时可达（native daemon，尚不存在）→ 对现有 OpenSSH 用户**零影响**。
- 顺带一致化：`stop()` 原用 `TunnelState::clear()`（读 VB_PROFILE 环境变量），而状态是用
  `self.profile` 加载的 → 改为 `clear_with_profile(self.profile.as_deref())`，
  与 load/save 同一 profile 作用域。

测试：`verdict_mapping_is_total_and_conservative`（四 Verdict 全映射，可移植）、
`unverifiable_identity_keeps_the_state_file`，并更新既有测试到新 Skip 结构。
验收门：fmt ✓ / clippy `-D warnings` ✓ / `cargo test` 0 failed（lib 684）✓ / `git diff --check` ✓。

## ✅ Windows 进程身份 + 关闭盲信 PID 缺口（提交 7a02f3e，已推送）

`identity.rs` 的 windows 分支由 `UnsupportedPlatform` 存根改为真实实现：
- `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + **`QueryFullProcessImageNameW`** 取镜像路径
  （选它而非 `GetModuleFileNameExW`：只需有限查询权限、**无需链 psapi**、对我们不拥有的进程也成功）
  + `GetProcessTimes` 取创建时间作 `start_identity`。
- 错误映射：`OpenProcess` 失败且 `GetLastError()==ERROR_INVALID_PARAMETER(87)` → `NoSuchProcess`；
  其余 → `Unreadable`。每条失败路径都 `CloseHandle`。
- **实现要点（易错）**：所有 Win32 调用**顺序平铺，不用闭包包裹** —— `unsafe` 块**不会延伸到闭包体内**，
  而该模块在 macOS 上根本不编译，这类错误无法靠本地构建发现。
- `FILETIME → u64` 拆成**跨平台纯函数** `filetime_to_u64(high, low)` 并加单测：
  windows 模块在本机无法类型检查，至少让其中唯一的真实逻辑可验证。
- 原始 FFI 声明（`extern "system"` + `#[repr(C)] FILETIME`）写在 `imp::ffi` 子模块，**无需新增依赖**。

`tunnel.rs` 关闭设计文档点名的缺口（非 unix 盲信 PID）：
- `verify_ssh_pid` 新增 windows 分支：用 identity 取可执行路径判 `is_ssh_executable`
  （该函数 cfg 由 `macos` 放宽为 `any(macos, windows)`）。
- `openssh_stop_decision` 由 `cfg(unix)`/`cfg(not(unix))` 改为
  `cfg(any(unix, windows))` 校验、**其余平台才盲信** → Windows 上 `tunnel stop`
  不再无条件 `taskkill /F` 一个可能是别人的 PID。

⚠️ **本机 macOS，windows 分支未编译验证（整段在 cfg 外）。上线前必须在 Windows 上构建一次。**

### 复用教训
- **`git status` 报告 cherry-pick in-progress 不等于真的有 in-flight 操作** —
  sequencer 目录可能因之前完成/abort 后清理不彻底而残留。
  先 `git rev-parse HEAD` 对比 `origin/main` + `git diff HEAD --stat` 确认工作树真实状态，
  再决定用 `--continue` / `--abort` / `--quit`。
  `--quit` 与 `--abort` 的区别：abort 会重置回 cherry-pick 前的 HEAD，
  quit 仅清 sequencer 状态、保留当前 HEAD 和索引。
