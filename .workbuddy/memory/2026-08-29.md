### 关键代码事实（供后续复用）

- `SSHRunner` (`src/transport/ssh.rs:179`) 的方法面与 spec 的 `RemoteTransport` 契约高度对应：
  `test_connection` / `run_command` / `upload` / `upload_text` / `download` / `download_dir`。
- `SSHRunner` 调用面收敛：仅 spectre/runner.rs、models.rs、transport/x11.rs、transport/tunnel.rs、
  src/tests.rs、commands/diag.rs、commands/maestro.rs、commands/sim.rs；`tests/` 下零引用。
- `src/transport/x11.rs` **不做任何端口转发**（无 `-R` / `ForwardX11` / `bind`），
  只做 DISPLAY 探测 + `upload_text`，所以把 X11 放在 RemoteTransport 之上是准确的。
- `VirtuosoClient::execute_skill` (`src/client/bridge.rs:225-274`) 内含**最多 10 次的
  同请求重发循环**：`for _ in 0..10u8` 里**每次迭代都新建 TcpStream**（`:226-228`），
  收到 `sync_N` 样式的陈旧票据（`is_stale_sync`, `:811`）就丢弃、换新连接重发同一条
  `req_bytes`（`:233`）。
  ⚠️ **不可断言**"传输层重连必然产生 `sync_N`"：`sync_N` 全库只在 bridge.rs 出现
  （`resources/daemons/*.py`、`ramic_bridge.il` 均无），生产方是未 vendored 的上游
  CIW 侧 bridge。可证明的只有"每次重发 = 新 TCP 连接"这一结构事实。
  → 真正的可证明风险：OpenSSH `-L` 下"新建 TCP 连接"廉价且近乎无状态；native
  `direct-tcpip` 下每次 accept 都是新 channel + 新远端 socket，客户端这条隐含假设被改变。
- `src/spectre/runner.rs:816-865` `run_parallel`：**所有 worker 共享一个** `Simulator`
  → 一个 `SSHRunner`。代码在 `thread::scope` **外**只 clone 一次（`:824 let sim = self.clone();`），
  作用域内闭包按 `&sim` 借用（`:839-844`）。每个 worker 在自己的 chunk 内**顺序**执行
  （`:840-847`），所以并发在途远端操作数 ≈ worker 数，而非 worker 数 × 每 job 命令数。
  ⚠️ `:797-798` 的 doc comment 声称 "each worker gets its own SSHRunner clone，
  use_control_master state is isolated per thread"——**与代码不符，是陈旧注释**。
  实际 `use_control_master: Mutex<bool>` 跨 worker 共享，注释宣称的隔离性并不存在
  （Mutex 保证无 data race，但没有隔离）。抽取抽象时别照着注释设计 per-worker 隔离。
  → 教训：**读代码，不要读 doc comment 下结论。**（本次审核 B2 判错的根源）
- `verify_ssh_pid` (`src/transport/tunnel.rs:88-102`) 在非 unix 下直接 `return true`
  （"fall back to trusting PID"），Windows 侧无进程身份校验机制。
- `TunnelState` (`src/models.rs:338`) 已有 `version` 字段 + profile 分片 + legacy fallback，
  是 spec state 模型的现成宿主，但 v2 迁移方案 spec 未提。
- `SessionInfo::sync_from_remote(&SSHRunner)` (`src/models.rs:282`) 是具体类型依赖，
  被 `commands/tunnel.rs:31` 与 `commands/session.rs:15` 调用。
- tokio 已在依赖内（`src/async_runtime.rs` + `src/session/heartbeat.rs`），
  但 feature 仅 `rt, rt-multi-thread, time`，缺 `net` / `io-util`。
- 测试基线：HEAD `083d4df` 上 `cargo test` 全绿（约 16s，三个二进制 581/731/574 + 集成，
  1 个 ignored：`ssh_runner_tests::integration_localhost_roundtrip`）。
  ⚠️ 用户环境有两个 profile 权限测试受沙箱限制需提权重跑；我的沙箱未复现。
  ⚠️ AGENTS.md 写的"369 unit + 116 integration"已过时，实际数量更高。
- 复核结论（用户第二轮）：原判 B2（并发契约）**核心事实有误，已撤回**；

### 1. `src/spectre/runner.rs:797-798` 陈旧注释已修正
改为如实描述：所有 worker 共享一个 clone（`&sim` 借用），每 worker 顺序处理自己的 chunk，
因此 `use_control_master: Mutex<bool>` 是共享而非按线程隔离。

### 2. `docs/superpowers/specs/2026-08-29-native-remote-transport-design.md`（325 → 580 行）
新增/重写章节：
- **Terminology** — 区分本地 transport daemon（`vcli __transport-daemon`）与远端
  `virtuoso-daemon`，两者同名不同机。
- **Concurrency and sharing** — `trait RemoteTransport: Send + Sync`（硬需求，非建议）；
  上层持 `Arc<dyn RemoteTransport>`；不得假设每线程一个 handle。
- **Capacity invariant** — `VB_SSH_MAX_SESSIONS >= VB_SPECTRE_MAX_WORKERS + control_reserve`
  （默认 10 >= 8+2 已满足）；违规时配置校验直接拒绝。
- **SKILL request retry policy**（新章节）— RemoteTransport 永不重放；默认
  `RetryPolicy::Never`；遇到 sync_N 且非幂等则返回 `OutcomeUnknown`；仅显式幂等探测可重发；
  幂等键属 RAMIC 协议升级，不能靠 transport generation 顶替。**未强制前，事务类 SKILL
  不得跑在 native 后端上。**
- **Stop and crash recovery** 改双层 — Tier1 daemon 应答 → IPC nonce 挑战；
  Tier2 失联强杀 → OS 身份三项匹配（路径+PID+启动标识）。平台三分支：
  Linux `/proc`+pidfd、**macOS 无 /proc 无 pidfd → libproc / sysctl KERN_PROCARGS2**、
  Windows `OpenProcess`+`GetProcessTimes`。
- **State-file versioning** — v1 缺 `backend` 推断为 openssh；之后一律写 v2；
  新增字段 `Option` 化以免自写反序列化器。
- **Commands affected by DaemonUnavailable** — 命令清单表格。
  ⚠️ **重要发现**：`src/commands/skill.rs:368,395` 与 `src/skill_finder/mod.rs:362,457,485`
  **直接 `Command::new("ssh")`，完全绕过 `SSHRunner`**。抽取 RemoteTransport 带不上它们，
  native 下会静默仍走 OpenSSH（后端泄漏，绕过 SOCKS5 与 daemon）。
- 其余：UDS 路径长度上限 + hash 短名回退；`VB_DISABLE_CONTROL_MASTER` 在 native 下
  `not_applicable` 不报错；feature 关闭返回 `UnsupportedBackend`（错误模型已加该码）；
  `upload_text` 改受保护临时文件传路径+长度+hash；目录传输两后端都依赖 tar（非分歧）。
- **Delivery sequence 重排** — 新增 step 0（契约测试先在 OpenSSH 后端跑通，作为 gate）
  与 step 3（单跳 SSH server fixture 先于被测代码落地），后续步骤只扩展 fixture。
